# Deskflow Flow Architecture

A proposal for how Deskflow stores, updates, and displays the state of all your work — Epics, Tasks, their plans, and their progress. This document is the complete specification. It replaces the earlier desk-as-truth model and is designed to survive multiple AI sessions writing state concurrently while you edit a live file.

---

## The Problem This Solves

Deskflow has two input channels: you editing a markdown file, and AI chat sessions making decisions and completing work. Both need to update the same logical state — the tree of Epics, Tasks, steps, and their statuses. The earlier architecture used the desk file itself as the source of truth, which worked when you were the only writer. It breaks the moment a chat session finalizes a three-phase plan or marks a step done, because now two writers are updating the same file with no merge semantics, and three different views (your checklist, a deep reference tree, and a live status board) all need to reflect a consistent picture.

The fix is a clean separation: **structured data files hold truth, your desk is an input surface and a generated view, and the engine is the only thing that writes truth.** Both input channels — your file edits and AI session decisions — flow into truth through well-defined operations, and all views render from truth. No view is truth; no input surface is truth.

## The Registry: FLOWS.json

One file at `flows/FLOWS.json` serves three purposes:

**Ranked order.** An array of flow IDs in priority order. This is the single home of "what comes first" — every surface that shows flows in order reads from here, and reordering flows in any editable view writes back here.

**Metadata.** Each flow entry carries its display name, kind (epic or task), slug, parent flow ID (for nesting), statement, and the relative path to its state file. This is how any consumer resolves an ID to its truth in one hop.

**ID allocation.** A ledger of every ID ever minted, ensuring global uniqueness. IDs are three lowercase letters, minted by the engine, collision-checked against this ledger. Existing two-letter IDs from the earlier system are accepted everywhere — the engine reads both widths but always mints three.

Epics exist here as registry entries only. They carry a name, statement, and parent links, but no separate EPIC.json — that schema is deferred until real use teaches what it needs to hold. Epic rows on the FLOWBOARD and in ALLTREE derive from the registry plus aggregation of their children's states.

## Flow State: TASK.json

Each task flow gets a folder under `flows/`, and its truth lives in `TASK.json`. This file holds topology and status — never long prose. It looks roughly like this:

```json
{
  "schemaVersion": 1,
  "id": "abc",
  "slug": "clean-ado-backlogs",
  "kind": "task",
  "name": "Clean Both ADO Backlog Trees",
  "statement": "Delivers cleaned two-tree ADO backlogs with ...",
  "parent": "dfm",
  "stage": 2,
  "createdAt": "260810-1412",
  "plan": {
    "phases": [
      {
        "name": null,
        "steps": [
          { "id": "qrs", "text": "Pull the current register",
            "parallel": true, "agent": "/compliance-inventorier",
            "status": "done" },
          { "id": "tuv", "text": "Flag stale items for review",
            "parallel": true, "agent": "/taskflow-subagent",
            "status": "active" }
        ]
      }
    ]
  },
  "chunks": [
    { "id": "wxy", "owner": "qrs", "kind": "detail",
      "path": "chunks/wxy.md" }
  ],
  "sessions": [
    { "name": "abc-phase1-a", "status": "ended" }
  ]
}
```

**Stages** track where a flow is in its lifecycle: `0` means no session has started working on it yet; `1` means its outcome, name, or statement is being clarified; `2` means its taskflow (the plan of phases and steps) is being designed; `3` means steps are being executed; `done` means done. Stage transitions are judgments made by sessions and recorded through engine commands — not computed.

**Plans** are sequential phases, each containing steps that may run in parallel. Phase names are optional — they render as "Phase 1," "Phase 2" when unnamed. Each step carries an `agent` (who does it), a `status`, and a three-letter ID that appears as a `[#xxx]` tag on the corresponding desk line. This is how checkbox flips in your file connect to step completions in the truth.

**Hierarchy** uses parent pointers. A task can be a child of another task or of an epic. An epic can be a child of another epic. The `parent` field in TASK.json points up; child lists and rollups are derived at render time by scanning, never stored. This avoids staleness — a stored children array would drift the moment a new child is created.

**Sessions** track which AI sessions have been spawned for this flow, so the FLOWBOARD can show session counts and the engine can prevent duplicate spawns.

## Chunks: Prose That Doesn't Belong in JSON

JSON is the right home for topology, status, and short strings. It is the wrong home for the paragraph of context you attached to a step, or the raw prompt you wrote that became a task, or the `[@ai]:` instruction you left on an item. These are **chunks**: verbatim markdown files stored under `chunks/` in the flow folder, referenced from TASK.json by owner ID and kind.

When ALLTREE.md renders a flow's full tree, it stitches topology from TASK.json with content from chunks — the JSON says what goes where, and the chunks say what it says. When you add a detail subtree under an item in ALLTREE, the engine saves it as a chunk file and adds a reference to TASK.json. Your prose round-trips losslessly without JSON ever holding structured markdown.

Chunk kinds include `detail` (your attached notes), `raw-prompt` (preserved original wording from elevation), `@ai` (your instruction bullets, consumed when handled), and `session-note` (observations from sessions).

## The Engine Command API

No AI session writes truth files directly. Instead, sessions call engine commands — shell invocations of the engine script — and the engine validates the input, acquires a lock, mutates truth, appends a receipt to CHANGELOG.jsonl, and schedules a view re-render. This is the single most important architectural decision in the proposal, because it replaces a protocol that LLMs violate (maintaining markdown file formats) with one they're good at (calling documented commands with arguments).

**Commands sessions use:**

| Command | What it does |
|---|---|
| `flow-create --kind --slug --name --statement [--parent] [--after]` | Mints an ID, scaffolds the flow folder, registers in FLOWS.json at the specified rank position. |
| `flow-get <id>` / `flows-list` | Reads truth as JSON — the read API. Sessions use this instead of opening state files. |
| `flow-set <id> --field value` | Updates statement, name, or other fields. |
| `stage <id> <n> ["reason"]` | Records a stage transition. |
| `plan-commit <id> --file <path>` | Installs a validated plan (phases, steps, agents) after user has approved the proposal. |
| `step <id> <stepId> <start\|done\|blocked> ["note"]` | Updates step status with attribution. |
| `ask <id> "question"` | Records a question for the user about this flow. |
| `answer <id> ["text"]` | Clears the pending question. |
| `session-register <id> --name` / `session-end <id> --name` | Maintains the session registry. |
| `note <id> "text"` / `signal <id> "text"` | Records observations; signals feed the self-improvement system. |
| `attach <id> <ownerId> --kind [--file\|stdin]` | Creates a chunk file and adds its reference to TASK.json. |

**Commands you use through just recipes:**

| Recipe | What it does |
|---|---|
| `desk-doctor` | Checks prerequisites, reports versions or install commands. |
| `desk-fresh` | Morning routine: archives yesterday's desk, instantiates today's operations from the template, records the daily board snapshot. |
| `desk-open` | Opens DESK.md in VS Code. |
| `desk-watch` | Starts the file watcher: detects your edits, re-renders views. |
| `desk-render` | One-shot view regeneration. |
| `desk-export` | Copies a clean, content-free deskflow/ for public sharing. |

**Concurrency.** Parallel sessions calling commands simultaneously are serialized by a mkdir-based lock (`system/.lock/`). The lock is atomic on both macOS and Windows, uses bounded retry with backoff, and detects stale locks from crashed processes. Within a flow, every CHANGELOG.jsonl entry carries a seconds-precision timestamp plus a monotonic sequence number, giving total ordering even when two events land in the same second.

**Commits.** Sessions no longer run `git add/commit/push` per exchange for truth files — concurrent pushes to shared state files are a conflict factory. Instead, the engine runs a debounced commit loop: after a burst of writes settles (roughly 500ms of quiet), it renders all views, commits everything that changed, and pushes once. A burst of three parallel step completions produces one render and one commit, not three.

## Your Desk: DESK.md

A stable file with a stable name. No more timestamped chain — truth lives in flow state files, history lives in git and CHANGELOG.jsonl, and the daily archive copy at `desk/archive/DESK_{yymmdd}.md` preserves your day-record ritual.

### Sections

The engine manages certain sections and leaves everything else alone. The rule is simple: **any `##` heading the engine doesn't recognize is yours — preserved verbatim, in position, across every write, forever.** So Waiting, Meeting Notes, Scratch, and anything you add next month persist without telling the engine about them.

Engine-managed sections at launch:

- **Operations Template** — you write cadence-tagged tasks and steps here; the engine reads them but never rewrites them. This is your template for recurring work.
- **Operations Today** — each morning, the engine instantiates due items from the template into fresh checkboxed lines here, based on cadence tags (`[daily]`, `[weekly:Mon]`, etc.).
- **Flowlists** — your working checklist of all active flows, rendered from truth in priority order. Fully editable under the contract below.
- **Inbox** — freeform capture space for writing that isn't tree-shaped yet. The engine reads it during processing passes and clears absorbed content with your approval.

### When the engine writes this file

Only at transaction moments: the morning `desk-fresh`, a /deskflow processing pass you invoked, or an explicit sync. Never on the continuous render loop — that's for FLOWBOARD and ALLTREE only. Between transactions, the file is entirely yours.

### How your edits survive engine writes

Every engine write re-reads the file fresh, regenerates only its own sections and its own generated lines within them, and preserves all your content in place. If the file changed on disk between the engine's read and its write attempt, it re-reads and re-merges rather than overwriting. The write itself is atomic (write to a temp file, then rename). User-edit detection works by diffing against a shadow copy the engine maintains at `system/.shadow/DESK.md`.

### What you can edit in Flowlists (and ALLTREE)

Every operation below is safe because ID anchoring makes each edit type unambiguous to the diffing engine:

1. **Flip checkboxes.** A checked `[#xxx]`-tagged line becomes a done event.
2. **Reorder lines.** Cut-paste ID'd lines into new positions; the ID sequence tells the engine exactly what moved where, including across parents.
3. **Insert new items.** A new checkboxed line with no `[#xxx]` tag is new intent. Its position between ID'd neighbors is the placement signal. The next /deskflow pass elevates its wording with you.
4. **Add details.** Plain child bullets (no checkbox, no tag) attach to their parent. The engine never parses inside your detail subtree — structure it however you want; it travels as a unit.
5. **Nest details freely.** Children of children of details, indefinitely.
6. **Reword existing items.** Same `[#xxx]` tag, changed text = a rename intent. The engine queues it for confirmation at the next processing pass rather than reverting it.
7. **`[@ai]:` bullets.** An instruction anchored to its parent item, written as if you're directing an AI about that item. Consumed when handled: the effect lands in truth, the bullet disappears.
8. **`~~Strike~~` to cancel.** An ID'd line wrapped in `~~` is a cancellation. The wording is preserved in truth; the item stops appearing in active views.

**What routes through `[@ai]:` or chat instead:** splitting one item into multiple, merging multiple into one, or changing step sequencing (parallel vs. sequential). These are topology changes where intent can't be reliably inferred from a text diff.

**What self-heals rather than erroring:** deleting an ID'd line outright (it reappears at the next render, since truth still holds it — strike is the delete that sticks), or editing a pure-status field like a stage number or timestamp (measurement, not authored content — the next render restores it silently).

## Views

### FLOWBOARD.md

A generated status board you keep open in a locked Markdown preview pane. Never edited. Re-rendered within about 500ms of any truth change.

Shows every active Epic and Task in a table with columns for stage (0/1/2/3/done), number of sessions spawned, and the latest question waiting on you — derived live by scanning each flow's CHANGELOG.jsonl for the most recent `ask` without a subsequent `answer`. When no question is pending, the column is empty. No staleness risk because it's computed on every render, never stored.

### ALLTREE.md

A deep reference view showing everything the system knows about every flow — statements, plan phases, steps, agents, attached details, status — organized under foldable `[heading]:` sections. Rendered live like the FLOWBOARD, but editable under the same contract as Flowlists (§ above). Kept as a separate file so it can refresh on the live render cadence; an in-desk section could only refresh at transaction moments and would sit stale between /deskflow passes.

When a field is edited in both ALLTREE and the desk's Flowlists between renders, the later edit wins and the collision is reported in the next /deskflow pass — rare in practice since you'll be looking at one surface at a time, but defined rather than undefined.

## Ordering

Flow order has one home: the ranked array in FLOWS.json. Every surface — FLOWBOARD rows, ALLTREE sections, Flowlists grouping — renders from it. When you reorder flows in an editable view, the engine updates FLOWS.json.

Within a flow, phases are sequential by definition. Step order within a phase expresses priority (which to start first, which matters most), not sequencing — steps in a phase may run in parallel. Changing whether steps are parallel or sequential is a topology change that routes through `[@ai]:` or chat, not a reorder.

---

## Operations

You define recurring work in the **Operations Template** section of DESK.md: tasks and steps tagged with cadences like `[daily]`, `[weekly:Tue]`, `[responsively]`. Each morning's `desk-fresh` reads the template, checks which items are due based on the current day, and instantiates fresh copies with checkboxes into the **Operations Today** section. Operations instances are daily ephemera — they get their own short-lived IDs, their done events are receipted, but they don't create flow folders. IDs retire at day end.

---

## Three-Letter IDs

Every flow and every step gets a three-letter ID: three lowercase letters, globally unique across the entire system, minted by the engine from the allocation ledger in FLOWS.json. They appear as `[#abc]` tags at the end of lines in editable views, and they are the identity anchor that makes every editing operation unambiguous.

The contract with you: never type, retype, duplicate, or edit an ID tag. Move lines whole with cut-paste. The engine creates IDs; you just carry them. Existing two-letter IDs from the earlier system are accepted everywhere — the engine reads both widths but only mints three-letter going forward.

## Migration

The current workspace runs an earlier Deskflow with a different truth model. Migration is guided and conversational, not scripted — the companion guide (`260810-migration-care-package-guide.md`) is written directly to the AI performing it, with instructions to inventory before proposing, propose before writing, and treat whatever it finds on disk as reality rather than assuming any particular state.

The essential moves: existing desk content becomes flows via `flow-create`; existing plan structures install via `plan-commit`; attached prose becomes chunks; the desk file transforms from a timestamped truth-carrying chain into a stable generated-plus-input surface; and superseded files (EPICS.md, ledgers, per-session events) archive rather than delete.

All five skills and agents (deskflow, taskflow-planner, taskflow-subagent, deskflow-copilot-cli, taskflow-diagram) need integration updates — primarily switching from direct file writes to engine commands, and from reading desk files as truth to reading flow state via `flow-get`. The migration guide carries per-file briefs specifying what each must start doing, stop doing, and read differently.
