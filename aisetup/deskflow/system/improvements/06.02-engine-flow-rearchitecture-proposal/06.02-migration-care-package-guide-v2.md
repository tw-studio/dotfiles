# Deskflow Migration Guide

You are an AI agent in a workspace running an earlier version of Deskflow. This guide walks you through migrating it to the flow architecture described in the companion proposal. Read that proposal in full before starting — it is the specification; this guide is the path.

The migration is not a script you run. It is a guided, conversational process where you inventory what exists, propose a plan, get user's approval, and execute in stages with git checkpoints between each one. The workspace has diverged from whatever state the proposal's author last saw, so you must discover rather than assume.

---

## Principles

**Inventory before proposing.** Your first job is to understand what actually exists on disk — file names, section names, content, ID usage, engine capabilities. Do this silently with your tools. Present findings, not questions about things you could have checked yourself.

**Propose before writing.** After inventory, present a concrete migration plan with numbered judgment calls. User approves before any file changes.

**Nothing is destroyed.** Superseded files move to an archive location user approves. Nothing is deleted. If something goes wrong, every prior state is recoverable.

**Git checkpoint per stage.** Commit before and after each migration stage. Use descriptive messages like `[deskflow-migration]: Stage 2 complete — truth files constructed`. This makes any stage independently revertible.

**Local reality wins.** Where this guide's expectations conflict with what you find on disk, what you find is correct. Report the divergence, adapt your plan, and note it for the proposal's next revision.

## Stage 1 — Inventory

Before you say anything to the user about migration, gather the following by reading files and listing directories. Present your findings as a structured report.

### 1a. Desk files

Look in `deskflow/desk/` (or `taskflows/desk/` if the rename hasn't happened). Answer:

- Are there timestamped desk files (`DESK_{yymmdd}-{hhmm}.md`)? How many? What date range?
- Is there already a stable `DESK.md`?
- What `##` section headings exist in the most recent desk file? List them all. Note which ones contain live work items (checkboxed lines with content) versus which are empty or structural.
- Is there an archive subdirectory? What's in it?

### 1b. Epic and task registry

Look for `EPICS.md` (could be at `deskflow/epics/EPICS.md` or `taskflows/epics/EPICS.md`). If it exists:

- How many rows? List the epic names, types (if the Type column exists), and folder slugs.
- Is there already a `FLOWS.json`? If so, what's in it?

### 1c. Per-epic folders

List every folder under `epics/` (or wherever epic folders live). For each:

- Does it contain a `ledger.md`? What's in it — task statements with IDs?
- Does it contain plan files (`.md` files with task breakdown tables)? List them.
- Does it contain `events.md` or any event log files?
- Does it contain subfolders like `planning/`, `done/`, `cut/`?

### 1d. ID usage

Scan all desk files, ledgers, and plan files for `[#xx]` and `[#xxx]` tags. Report:

- How many unique IDs exist?
- Are they two-letter, three-letter, or mixed?
- Any duplicates? (This matters — duplicates must be resolved before migration.)

### 1e. Engine

Find the engine file (likely `deskflow/system/deskflow-engine.js` or similar). Report:

- Is it a single file or already modular (`system/engine/` directory)?
- What verbs does it dispatch? (Read the dispatch map or `verbs` object near the bottom.)
- Does it have a `doctor` verb? An `export` verb? A `watch` verb?

### 1f. Skills and agents

Check both `.claude/skills/` and `.github/agents/` (or `.github/chatmodes/`). For each of these, report whether it exists as a skill, an agent, both, or neither:

- `deskflow` — the main orchestrator
- `taskflow-planner` — plans taskflows from outcomes
- `taskflow-subagent` — runs inside spawned copilot sessions
- `deskflow-copilot-cli` — manages copilot CLI session spawning
- `taskflow-diagram` — generates text diagrams of taskflows

Also note any other skills or agents that reference deskflow files, read the desk, or write state.

### 1g. Settings and justfile

- Does `deskflow/system/settings.md` exist? What keys does it carry?
- Which `desk-*` recipes exist in the workspace justfile? What does each invoke?

### 1h. Other

- Is there a `TASKBOARD.md`? Where?
- Is there a `.gitignore` in the deskflow folder? What does it ignore?
- Any files or structures not covered above that look like they carry live state?

**Present all of this as a single structured report.** Do not start proposing migration steps yet. Let user review and correct the inventory first.

## Stage 2 — Migration Plan

From the inventory, build and present a migration plan. This plan must cover:

### What becomes a flow

Every epic and every task that has its own identity (a name, a statement, or even just a rough line in the desk) becomes a flow with its own folder under `flows/`. Walk the inventory's epic list and desk content top-down and propose, for each item:

- **Kind:** epic or task.
- **Name and slug:** derived from the existing name; propose the kebab slug.
- **Parent:** which flow is its parent, if any. Tasks under epics point to the epic. Tasks under tasks point to the parent task.
- **Stage:** infer from current state — does it have a clarified outcome? A plan? Active work? Infer the stage (0/1/2/3/done) and state your reasoning.
- **Existing IDs to preserve:** if the item already has a `[#xx]` tag, that ID carries over.
- **Content to migrate:** ledger entries, plan file contents, attached descriptions, event history.

Number every item so user can veto or correct individual entries.

### What becomes an operation

Items in any Operations-style section with cadence tags become entries in the Operations Template section of the new DESK.md. List them.

### What archives

List every file that the new architecture supersedes, with the proposed archive destination. Typical candidates:

- `EPICS.md` (absorbed by FLOWS.json)
- `ledger.md` files (absorbed by TASK.json)
- Per-session `events.md` files (absorbed by per-flow CHANGELOG.jsonl)
- `engine-events.md` (absorbed by per-flow changelogs)
- Old timestamped desk files (the latest becomes the seed for DESK.md; older ones stay in `desk/archive/`)
- `TASKBOARD.md` (replaced by FLOWBOARD.md)

### What the new desk looks like

Propose the section list for the new DESK.md, mapping old sections to new ones:

| Old section | New section | Notes |
|---|---|---|
| Epics Today / similar | Flowlists | Rendered from truth; editable under contract |
| Done Today | (archived with the day) | Done handling moves to engine bookkeeping |
| Operations Today | Operations Today | Engine-instantiated from template |
| Operations-related template content | Operations Template | User-owned; engine reads cadence tags |
| One-offs & Inbox / similar | Inbox | User freeform; engine absorbs during processing |
| Waiting, Meetings, Scratch, etc. | Preserved verbatim | User-owned sections carry over as-is |

### Execution order

Propose the order of stages 3–7 below, noting any dependencies. The typical order is: engine first (so commands are available), then truth construction (so there's data), then surfaces (so there's something to see), then skill updates (so sessions use the new system), then verification.

**Present this plan. Proceed only on user's approval.**

## Stage 3 — Build the Engine

The v2 engine is a module tree at `deskflow/system/engine/`. It replaces the single-file engine entirely. This is the heaviest implementation stage.

### Entry point

`deskflow-engine.js` — argument parsing and verb dispatch. Every verb is a function in a `lib/` module. The justfile's `engine :=` path updates to point here.

### Modules to implement

| Module | Responsibility | Key details |
|---|---|---|
| `lib/lock.js` | Serialized writes via `mkdir` on `system/.lock/`. | Bounded retry with exponential backoff. Stale-lock detection: if the lock directory's mtime is older than 30 seconds, assume the holder crashed and take over. Works identically on macOS and Windows. |
| `lib/store.js` | Load, validate, and save FLOWS.json and TASK.json files. | Every write is atomic: write to a temp file in the same directory, then `fs.renameSync` over the target. This prevents partial writes on crash. Validate against schema before every save; reject and report on failure. |
| `lib/schema.js` | JSON schemas for FLOWS.json and TASK.json. | Export `validateFlows(data)` and `validateTask(data)` functions that return `{ valid, errors }`. `schemaVersion` field enables forward migration. |
| `lib/changelog.js` | Append entries to a flow's CHANGELOG.jsonl. | Each entry: `{ ts, seq, actor, verb, payload }`. `ts` is seconds-precision ISO. `seq` is a monotonic integer per file, read from the last line on append. `actor` is the session name or `engine` or `user`. |
| `lib/ids.js` | Mint three-letter IDs, check collisions against the FLOWS.json allocation ledger. | Accept two-letter IDs on read (grandfathered). Mint only three-letter. Never mint an ID that appears anywhere in the ledger, even if the original flow was deleted. |
| `lib/desk.js` | Parse DESK.md sections, detect user edits by diffing against the shadow copy, write merged updates. | The section-ownership rule: recognized `##` headings are engine-managed; everything else is user-owned, preserved verbatim in position. The shadow copy at `system/.shadow/DESK.md` is the diff baseline, updated after every successful engine write. |
| `lib/render.js` | Generate FLOWBOARD.md and ALLTREE.md from truth. | Debounced: after any truth write, wait ~500ms of quiet before rendering. FLOWBOARD reads FLOWS.json, all TASK.json files, and scans changelogs for pending asks. ALLTREE reads the same plus chunks. |
| `lib/chunks.js` | Create, read, and reference chunk files in a flow's `chunks/` directory. | Each chunk is a markdown file with YAML frontmatter: `owner` (the ID of the item it belongs to), `kind` (detail, raw-prompt, @ai, session-note), `created`. |
| `lib/ops.js` | Operations Template → Operations Today instantiation. | Reads the template section from DESK.md, checks cadence tags against today's day of week, creates checkboxed lines with minted daily-scoped IDs. |
| `lib/time.js` | Timestamp formatting. | `Dy.yymmdd`, `yymmdd-hhmm`, `yymmdd-hhmmss`, ISO seconds. |
| `lib/derive.js` | Compute derived data: pending asks, child lists, epic rollups. | `pendingAsk(changelog)`: scan tail for latest `ask` without a later `answer`. `children(flowId, allFlows)`: filter by parent pointer. `epicStage(epicId)`: aggregate children's stages. |

### Verb dispatch table

The entry point maps CLI arguments to module functions. The full verb set:

**Session-facing verbs** (called by AI sessions via terminal):

- `flow-create --kind <epic|task> --slug <s> --name <n> --statement <s> [--parent <id>] [--after <id>]`
- `flow-get <id>` — prints the flow's TASK.json (or registry entry for epics) as JSON to stdout
- `flows-list` — prints FLOWS.json to stdout
- `flow-set <id> --field <f> --value <v>` — updates a specific field
- `stage <id> <0|1|2|3|done> ["reason"]`
- `plan-commit <id> --file <path>` — reads a JSON file containing the plan structure, validates, and installs
- `step <id> <stepId> <start|done|blocked> ["note"]`
- `ask <id> "question text"`
- `answer <id> ["response text"]`
- `session-register <id> --name <session-name>`
- `session-end <id> --name <session-name>`
- `note <id> "text"` / `signal <id> "text"`
- `attach <id> <ownerId> --kind <k> [--file <path>]` (reads stdin if no --file)

**User-facing verbs** (called through just recipes):

- `doctor` — prerequisite checks with install hints
- `fresh` — morning routine: daily archive, operations instantiation, board-history record
- `open` — opens DESK.md in VS Code
- `watch` — starts the file watcher for continuous rendering
- `render` — one-shot view regeneration
- `export` — content-free copy for public sharing
- `snapshot-cleanup` — prunes old snapshots

### Porting from the old engine

The old single-file engine likely has working implementations of `doctor`, `fresh`, `open`, `watch`, `render`, `export`, and `snapshot-cleanup`. These can be ported into the new module structure, adapted to read from FLOWS.json and TASK.json instead of EPICS.md and desk files. The session-facing verbs are entirely new.

### Testing before touching real data

After building the engine, verify the round-trip before proceeding:

1. `doctor` runs clean.
2. `flow-create --kind task --slug test-flow --name "Test Flow" --statement "Tests the engine."` succeeds, creates a folder under `flows/`, and registers in FLOWS.json.
3. `plan-commit` on the test flow with a small plan JSON succeeds and validates.
4. `step` start and done on a plan step succeeds and receipts to CHANGELOG.jsonl.
5. `render` produces a FLOWBOARD.md and ALLTREE.md that reflect the test flow.
6. Delete the test flow's folder and its FLOWS.json entry. Commit as `[deskflow-migration]: Engine verified, test flow cleaned`.

## Stage 4 — Construct Truth

This is where existing content becomes flows. Work through the migration plan from Stage 2, item by item, with user confirming as you go.

### For each epic

1. Call `flow-create --kind epic --slug {slug} --name "{name}" --statement "{statement}"` with `--after` if rank ordering was specified. If the epic already had a two-letter ID, you cannot force the engine to use it — the engine mints a new three-letter ID. Map the old ID to the new one and track the mapping for desk content migration.
2. There is no EPIC.json to populate. The registry entry in FLOWS.json is the epic's entire truth for now.

### For each task

1. Call `flow-create --kind task --slug {slug} --name "{name}" --statement "{statement}" --parent {epicId}` with rank positioning.
2. If the task had a plan (phases and steps) in a plan file or ledger:
   - Convert it to the TASK.json plan structure: an array of phases, each with an array of steps carrying `id`, `text`, `parallel`, `agent`, and `status`.
   - Write this as a temporary JSON file.
   - Call `plan-commit {taskId} --file {path}` to install it.
   - Delete the temp file.
3. If the task had attached descriptions, `[description]:` children, or preserved `[Raw Prompt]:` blocks:
   - Write each as a markdown file.
   - Call `attach {taskId} {ownerId} --kind detail` (or `raw-prompt`) for each.
4. If event files record done/stage/blocked history for this task:
   - Replay significant events as changelog entries: `stage`, `step done`, `note` with attribution to `migration`.
   - This preserves the historical record in the new format.

### ID mapping

Keep a local mapping file (temporary, migration-only) of old two-letter IDs to new three-letter IDs. You'll need this when transforming desk content in Stage 5, because lines in the desk carry old `[#xx]` tags that must be replaced with the new `[#xxx]` tags.

## Stage 5 — Build Surfaces

### DESK.md

Take the most recent desk file's content and transform it into the new DESK.md:

1. **Operations Template section.** Extract any cadence-tagged recurring items from the old desk and write them here with their tags preserved.
2. **Operations Today section.** If today's operations were already instantiated in the old desk, carry them over. If not, leave empty — the next `desk-fresh` will populate it.
3. **Flowlists section.** Render from truth: call `flows-list`, read each TASK.json, and generate the checklist in priority order. Each line gets the flow's new `[#xxx]` tag. Nest tasks under their parent epics as sublists.
4. **Inbox section.** Any content from the old desk that doesn't map to a flow or an operation goes here as-is, preserving user's wording exactly.
5. **User-owned sections.** Every `##`-headed section from the old desk that isn't covered above carries over verbatim: Waiting, Meetings, Scratch, and anything else. Position them where user expects them — propose the order and let user adjust.

Create the shadow copy at `system/.shadow/DESK.md` as an identical copy of the freshly written DESK.md.

### FLOWBOARD.md

Call `render` or implement the render logic: read FLOWS.json and all TASK.json files, generate the status table with columns for name, stage, session count, and pending question (derived from changelogs). Write to `deskflow/FLOWBOARD.md`.

### ALLTREE.md

Same render pass: the full tree with foldable sections, plan details, chunk contents stitched in, status per step. Write to `deskflow/ALLTREE.md`.

### .gitignore updates

Ensure `deskflow/.gitignore` includes:

```
FLOWBOARD.md
ALLTREE.md
system/snapshots/
export/
```

DESK.md is tracked (it carries user content). FLOWBOARD and ALLTREE are generated and should not be tracked — they regenerate from truth on any machine.

### Justfile updates

Update the `engine :=` line to point to the new engine entry point. Add any new recipes (`desk-doctor` if missing, etc.). Remove any recipes that invoked retired verbs.

## Stage 6 — Update Skills and Agents

Each skill and agent file in the workspace needs behavioral changes to work with the new architecture. Since these files have diverged locally, you cannot replace them wholesale — you must re-synthesize each one, folding in the required changes while preserving local customizations.

For each file below, read the current version in full, understand its local state, then re-synthesize it incorporating the required changes. Present each re-synthesized file to user for approval before writing it.

### deskflow (skill and agent)

The main orchestrator. Carries the heaviest changes.

**Must start doing:**
- Use engine commands (`flow-create`, `flow-set`, `stage`, `plan-commit`, `step`, `ask`, `attach`) as the exclusive write path for all state changes. No direct writes to any JSON, JSONL, or generated view file.
- Read flow state via `flow-get` and `flows-list`, never by opening TASK.json directly.
- Reference DESK.md as a stable file — no more creating timestamped desk stamps. When processing is complete, call the engine's desk-write mechanism, which handles the merge and shadow update.
- Use the v2 stage vocabulary: 0 (not started), 1 (clarifying), 2 (planning), 3 (implementing), done.
- Process `[@ai]:` bullets as anchored instructions about their parent items.
- Interpret `~~struck~~` ID'd lines as cancellation intents.
- Interpret same-ID changed-text lines as rename intents, queuing them for confirmation.

**Must stop doing:**
- Writing or stamping timestamped DESK files.
- Writing EPICS.md, ledger.md, or events.md files.
- Running `git add/commit/push` per exchange for truth files. The engine owns commits now.
- Referencing the TASKBOARD (now FLOWBOARD, and generated by the engine).

**Must read differently:**
- Truth comes from `flow-get`/`flows-list` output, not from desk files or EPICS.md.
- The desk is an input surface and a partially-generated view, not the source of truth.
- Settings still come from `settings.md`.

### taskflow-planner (skill and agent)

Plans taskflows by designing phases and steps.

**Must start doing:**
- Conclude planning by writing a plan JSON file to the flow's `02-proposals/` folder, then calling `plan-commit {flowId} --file {path}` after user approves the proposal .md.
- Use the TASK.json plan structure: phases (with optional names) containing steps (with `id` minted by the engine via a pre-allocation call or assigned by `plan-commit`, `text`, `parallel` boolean, `agent`, `status`).
- Record stage transitions via `stage {flowId} 2` when planning begins.

**Must stop doing:**
- Writing plan markdown files as truth. Proposal .md files remain review artifacts in `02-proposals/` — they're for user's eyes, not the engine's.
- Inventing step IDs. The engine mints them globally.

### taskflow-subagent (skill)

Runs inside spawned copilot sessions to accomplish steps.

**Must start doing:**
- On spawn: `session-register {flowId} --name {sessionName}`.
- On starting a step: `step {flowId} {stepId} start "beginning work"`.
- On completing a step: `step {flowId} {stepId} done "what was accomplished"`.
- On blocking: `step {flowId} {stepId} blocked "what's blocking"`.
- When it has a question for user: `ask {flowId} "the question"`.
- For observations and sentiment: `note {flowId} "text"` / `signal {flowId} "text"`.
- On session end: `session-end {flowId} --name {sessionName}`.
- Read its assigned flow's state via `flow-get {flowId}`.

**Must stop doing:**
- Writing to events.md files.
- Reading desk files or plan markdown as truth.
- Running git commits for state files.

### deskflow-copilot-cli (skill)

Manages spawning of copilot CLI sessions.

**Must start doing:**
- Pass the flow ID and a verb quick-reference to spawned sessions so they can call engine commands.
- Use `session-register` before spawning and pass the session name to the subagent.

**Must stop doing:**
- Seeding sessions with events.md conventions or desk-file reading instructions.

### taskflow-diagram (skill)

Generates text diagrams of taskflows.

**Must start doing:**
- Read topology from `flow-get {flowId}` JSON output: phases, steps, parallel flags, agents, statuses.
- Use the v2 stage vocabulary for any status display.

**Must stop doing:**
- Parsing plan markdown files for structure.

## Stage 7 — Verification

Run each of these checks and report results to user. Every check must pass before migration is declared complete.

1. **`desk-doctor` clean.** All required tools present, versions reported.

2. **Checkbox round-trip.** Open DESK.md, flip a checkbox on an ID'd line, save. Confirm: the engine detects the change (visible in watch output or by checking the flow's CHANGELOG.jsonl for a `step done` entry), and FLOWBOARD.md updates to reflect the new status.

3. **In-place rename.** In Flowlists, change the text of an ID'd line (keeping the `[#xxx]` tag). Save. Confirm: the engine detects a rename intent (logged or visible in the next processing pass), and the original wording is not silently restored on the next render.

4. **New item insertion.** In Flowlists, add a new checkboxed line (no ID tag) between two existing items. Save. Confirm: the next /deskflow processing pass picks it up as new intent and proposes to elevate it.

5. **`[@ai]:` consumption.** Add an `[@ai]: split this into two tasks` bullet under an existing item. Confirm: the next processing pass surfaces it as an instruction and acts on it (or proposes action).

6. **Pending question.** From a terminal, run `ask {someFlowId} "Test question for user"`. Confirm: FLOWBOARD.md shows the question in the flow's row. Then run `answer {someFlowId}`. Confirm: FLOWBOARD.md clears the question.

7. **Parallel step completion.** Open two terminal windows. In each, run `step {flowId} {differentStepId} done "test"` as close to simultaneously as practical. Confirm: both events are receipted in CHANGELOG.jsonl with correct attribution and sequential monotonic sequence numbers. FLOWBOARD.md reflects both completions. Only one git commit was produced (debounce working).

8. **Desk preservation.** Confirm that user-owned sections (Waiting, Meetings, Scratch, anything custom) survived the migration with their content intact and in the expected position.

9. **Archive recovery.** Confirm that every superseded file (old desk chain, EPICS.md, ledgers, event files) is recoverable from the archive location.

10. **Cross-machine readiness.** Commit and push. On the other machine (or a fresh clone), confirm: `desk-render` regenerates FLOWBOARD.md and ALLTREE.md correctly from the truth files alone.

## After Migration

- The next `desk-fresh` should instantiate operations from the template and create a daily archive snapshot — verify this works on the first morning after migration.
- The first `/deskflow` run after migration should process the Flowlists and Inbox sections using the new editing contract. Watch for any content that the engine fails to parse correctly and report it.
- TASK.json fields will evolve in the first weeks of use. The `schemaVersion` field exists so the engine can migrate state files forward automatically — resist adding fields preemptively; let real use reveal what's needed.
- If anything in this guide contradicted what you found on disk, you noted the divergence per the ground rules. Compile those notes into a brief for the proposal's next revision.
