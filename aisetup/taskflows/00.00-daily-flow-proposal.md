# Daily Flow Proposal

Proposed lifecycle for the daily working files that serve as user's primary work surface until the Taskflows app exists. Canon already settled in fundamentals: files live in `taskflows/focus-areas/daily/` as `focus-areas-{yymmdd}-{hhmm}.md`, at most one is live at a time, and no agent ever edits the live file. Everything below is proposal.

## Core Idea

The daily file is user's freeform thinking surface — specify, organize, reorder, plan, replan, reclarify anything, in whatever rough form the moment produces. The system then adapts to it, never the reverse: rough declarations get harvested into real taskflow files (the durable truth), and a fresh daily file gets stamped out reflecting the polished state. User's rough text is never edited in place by anyone — it gets *superseded*, and the old file remains untouched as a journal entry.

## Lifecycle

1. **Bootstrap.** A new day's first file is generated from FOCUS-AREAS.md ordering plus the current state of active taskflows across focus areas — focus areas in priority order, each with its active Outcomes, waiting-on-user items, and top next actions. Generated on user's command to start (auto-generation is an open decision).
2. **Live work.** User works in the file freely all day. No agent touches it.
3. **Harvest, on command.** User invokes the harvest (a slash command; name open). The harvest reads the live file and routes what it finds: focus-area reorderings → FOCUS-AREAS.md sync; rough Objective/Operation declarations with their Tasks → /taskflow-planner intake per focus area, which then drives planning per its own protocol to the point where user can efficiently weigh in; edits to existing plans → flagged to the relevant taskflow as proposed revisions.
4. **Regenerate.** After routing, the harvest stamps a new `focus-areas-{yymmdd}-{hhmm}.md` reflecting the processed state — polished wording, links to the taskflow files that now carry the real plans — and stores a snapshot of exactly what it consumed. User switches to the new file whenever ready, and can also force regeneration at any moment.
5. **Forward-carry.** If user kept editing the old file after a newer one was generated, the next harvest three-way merges: stored snapshot vs user's edited old file vs current system state. Because at most one file is ever live, the merge always has exactly one predecessor to consider — never a scan across the day's files.
6. **Journal.** Old daily files are never modified after supersession. They accumulate in `daily/` as an immutable record of how each day's thinking actually went.

## What Happens to Rough Declarations

Directly answering the open question: when user declares one Objective with three roughly-worded Tasks and agents later polish it into a proper taskflow with more tasks and better wording, the rough version's job is done. The taskflow file is the durable, authoritative artifact; the next daily file shows the polished state with a link; the rough original survives verbatim in the journal. Nothing needs merging back into user's prose, because user's prose was intake, not storage.

## Rejected Alternative

Agents editing the daily file directly so user reviews via git-diff experiences in VS Code. Rejected as the primary mechanism: it breaks the single-writer rule, reintroduces the exact conflict class user most wants structurally eliminated, and turns user's thinking surface into a contested file. Git diffs remain fully available anyway — every generated file is committed, so any two versions diff cleanly on demand.

## Trigger Mechanics — Recommendation

Start fully manual: harvest and regeneration run only when user invokes them. Promote to automation (cron for the morning bootstrap, possibly a commit hook for FOCUS-AREAS.md sync) only after the manual flow has proven itself for a stretch of real days. Debugging trigger automation on top of an unproven flow multiplies exactly the annoyances this design exists to prevent.

## Open Decisions

1. **Harvest command name** — `/focus-harvest`, `/daily-harvest`, or other.
2. **Morning bootstrap** — manual invocation for now per the recommendation; revisit auto-generation after the flow proves out.
3. **Old-day sweep** — whether `daily/` gets year-month subfolders once volume warrants, or stays flat.
4. **Harvest executor** — a dedicated `/daily-harvester` specialist versus a general `agent` following this proposal; specialist likely once the flow stabilizes.
5. **FOCUS-AREAS.md writer transition** — the moment the sync job takes over as its single writer, user stops hand-editing it; when to flip.
